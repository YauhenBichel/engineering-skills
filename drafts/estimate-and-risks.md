## Steps
1. State best, likely, and worst case hours. List core assumptions (e.g., clean workspace, API keys ready).
2. Name top three risks. Pair each with a reduction step (e.g., spike a prototype, add `pytest` integration tests, isolate legacy modules).
3. Separate known work from research. Assign hours to each. Flag unknowns.
4. Say what would change the estimate. List triggers (e.g., `uv sync` fails, scope adds auth, environment limits hit).
5. Give one sentence of recommendation: go, go with the first risk reduced, or do not start yet.

## Checklist
- [ ] Range covers best, likely, worst cases
- [ ] Each risk has a reduction step
- [ ] Known work separated from research
- [ ] Change triggers listed
- [ ] Assumptions are written, not implied

## Output
- Range with assumptions
- Risks and mitigations
- Known vs research split
- Change triggers and a one-line recommendation
